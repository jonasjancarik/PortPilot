# v3.1 - VS Code extension hosts the web portal

Goal: run the PortPilot web portal whenever VS Code is open, with no Electron
desktop app. The extension becomes the always-on host; MCP stays a control
surface (it cannot host an HTTP listener - it is a stdio process owned by the
client and dies on disconnect).

This is a UX upgrade on top of v3.0.0. v3.0.0 already runs the portal without
Electron via `npm run agent`; v3.1 removes the manual terminal step.

## Decision: spawn, do not embed

The extension SPAWNS and supervises a child Node process running the existing
standalone agent (`src/agent/server.js`). It does NOT embed `createAgent` in the
extension host.

- Spawn reuses the hardened agent verbatim (loopback-only bind, 256-bit
  per-session token, `agent.json` chmod 600). Because spawning runs the agent's
  `main()`, the auto port-fallback comes for free.
- Embedding would force bundling the whole `src/main` + `src/core` CommonJS tree
  into the TS extension (which today imports none of it) for zero benefit - the
  embedded agent's in-memory process table is still separate from any desktop
  app's.

Note: `createAgent({port})` itself binds the exact port and rejects on
EADDRINUSE. The `findAvailablePort` fallback lives in the CALLERS - the
standalone `main()` (`src/agent/server.js`) and the Electron `agent:start`
handler (`src/main/main.js`). Spawning `main()` inherits it; an embed would have
to replicate it.

## Implementation steps

1. **Ship the agent in the .vsix.** The extension currently ships none of
   `src/*`. Extend packaging so the full runtime closure lands in the vsix:
   `src/agent/server.js`, `src/core/dispatch.js`, `src/core/configPath.js`,
   `src/main/configStore.js`, `src/main/portScanner.js`,
   `src/main/processManager.js`, `src/main/ipcHandlers.js`,
   `src/main/projectScanner.js`, plus the `src/renderer` web UI assets. Verify
   the FULL transitive require closure (a miss = MODULE_NOT_FOUND at runtime).
   Resolve the absolute server path at runtime via `context.extensionPath`.
2. **Settings + commands** in `vscode-extension/package.json`:
   `portpilot.webPortal.enabled` (boolean, default `false` - opt-in so the
   listener is never spun up unannounced) and commands
   `portpilot.startWebPortal` / `portpilot.stopWebPortal`.
3. **Spawn with the editor's own Node** (no system Node dependency):
   `cp.spawn(process.execPath, [serverJsPath, '--no-open'], { env: { ...process.env, ELECTRON_RUN_AS_NODE: '1', PORTPILOT_NO_OPEN: '1' }, stdio: ['ignore','pipe','pipe'] })`.
   The agent already honours `--no-open` / `PORTPILOT_NO_OPEN`.
4. **Learn the chosen port + token** by reading the `agent.json` the child writes
   at `%APPDATA%/portpilot/agent.json` (more robust than stdout parsing; poll/await
   it to avoid racing the child's write). Surface the URL in a status-bar item +
   a notification with an "Open" action calling `vscode.env.openExternal`.
5. **Lifecycle:** push `{ dispose: () => child.kill() }` to
   `context.subscriptions` AND add an explicit `child.kill('SIGTERM')` in the
   currently-empty `deactivate()`. Optionally re-spawn on unexpected exit while
   `webPortal.enabled`.
6. **CRITICAL - teardown policy (the single most important detail).** The agent's
   standalone shutdown only calls `agent.stop()` (closes HTTP + SSE); it never
   calls `processManager.cleanupAllProcesses`, so killing the portal orphans the
   dev-servers it started. Pick and document one:
   - (a) Add a SIGTERM branch in `main()` that calls `cleanupAllProcesses` when an
     env flag (e.g. `PORTPILOT_STOP_APPS_ON_EXIT=1`) is set, mirroring the
     desktop's `stopAppsOnQuit` gate; or
   - (b) deliberately leave dev-servers running across portal restarts and rely on
     the port-scan matcher to re-detect them.
7. **Unify process ownership (recommended).** Change the extension's start path
   from the current VS Code terminal spawn to call the hosted agent's
   `process:start` over loopback with the `agent.json` token. That routes ALL
   starts through one agent, giving a single per-host process table and making
   stop-by-id work instead of the fragile port-scan-then-taskkill heuristic.

## Test matrix

- Portal reachable while VS Code is open.
- Clean window close runs `deactivate()` and kills the agent child.
- Abnormal kill (Task Manager / `kill -9` / sleep): `deactivate()` does NOT run -
  verify recovery via PortPilot's port-scan + kill-by-PID path.
- Two VS Code windows: second spawn hits EADDRINUSE on 7317, `findAvailablePort`
  picks the next free port - confirm the status bar shows the actual port from
  `agent.json`, not a hardcoded 7317.

## Known caveats / risks

- **Orphaned dev-servers on abnormal exit** is inherent to the model, not a bug.
  Mitigate with crash-restart supervision; document it.
- **`agent.json` is a single fixed-path file.** Two concurrent standalone agents
  overwrite each other's `{port,token,pid}`, and whichever exits first
  unconditionally `fs.rmSync`es it, leaving the survivor with no on-disk record.
  Consider per-instance `agent.json` naming if multiple concurrent agents are
  intended. (The Electron embedded agent never writes `agent.json` - only the
  standalone `main()` does - so this discovery path only ever sees
  standalone-spawned agents, which is exactly Option B.)
- **`ELECTRON_RUN_AS_NODE` quirks:** generally works but test on a clean machine
  with no system Node to confirm `process.execPath` works end to end.
- **Config write contention:** more concurrent hosts writing
  `portpilot-config.json` raises lost-update risk; confirm `ConfigStore` writes
  are atomic (temp-file + rename) before encouraging many simultaneous hosts.

## What stays true regardless

- Config (the apps registry) is shared via one fs-watched file; the live process
  table is in-memory and per-host.
- Detection is cross-host (two-phase port + CWD matcher), so apps show as running
  everywhere; but stop-by-id is owner-only, with kill-by-PID-from-scan as the
  universal fallback.
