=== DIAGNOSIS ===
1. SIGNAL DROWNED IN NOISE: The Active Ports tab renders all ~33 ports in one uniform two-column card grid. OS/system ports (:135 svchost, :139 System, :445 System PID 4) get identical visual weight to the user's real dev servers (:3000 node, :3001 node). There is no grouping, no sort, no classification, so the 2-3 ports the user actually cares about are buried among ~30 they must never touch. This is the headline flatness failure.
2. NO STATUS MODEL AT ALL: A port is either 'present in the grid' or absent. There is no running/stopped/starting/conflict/error vocabulary, no color, no glyph, no state word. Every card looks equally 'alive', so the eye cannot pre-attentively find the one server that matters or the one port that is in conflict. The redesign has to invent a status concept from scratch.
3. APPS SPLIT FROM THEIR LIVE PORTS: MY APPS (registered projects with start/stop) and ACTIVE PORTS (live scan) are two disconnected tabs. The core question 'is my registered app running, and on which live port' requires mentally joining two views. The intent (my app) and the runtime reality (its live port) never share a row.
4. EVERY CARD IS OVERLOADED YET TRUNCATED: Each card crams :PORT (large blue), PROCESS, PID, a truncated COMMAND, a copy icon, and a red kill X. That is the worst of both worlds: the card is visually heavy (five-plus competing elements, nothing reads as primary) AND it still truncates the one field (full command) you would open a card to read. There is no detail surface, so verbose data has nowhere to go but onto every card.
5. 66 ALWAYS-ON BUTTONS: The copy icon and red kill X are painted on all ~33 cards permanently. That is roughly 66 always-visible controls competing with the data and multiplying the wall-of-boxes feeling. Worse, an identical red kill X sits on OS/system ports (:445 System PID 4) that the user should never kill - a footgun with no friction.
6. HORIZONTAL TOP-TABS WASTE VERTICAL SPACE AND WILL NOT SCALE: ACTIVE PORTS | MY APPS | KNOWLEDGE | SETTINGS with a gold underline eats a horizontal band of vertical height and tops out around 5 tabs before wrapping. There is no room to add Logs, Groups, or future destinations.
7. FLAT SETTINGS STACK: SETTINGS is a vertical run of full-width bordered boxes (THEME, PREFERENCES, DATA) with no sub-nav. It is the same flatness problem in miniature. The 6 themes render as 6 identical text buttons that do not preview themselves. There is no room to grow (scan rules, web-portal auth, shortcuts, per-app config) without an ever-longer scroll.
8. CARD GRID DEFEATS COMPARISON: A two-column card grid forces the eye to re-read every box because PORT/PROCESS/PID/COMMAND sit in different positions within each card. There is no aligned column to scan down, so you cannot answer 'which of these is node' or 'which is on a high port' without reading all 33 cards individually.
9. FLATNESS IS REPLICATED ACROSS THREE SURFACES: Desktop, VS Code extension, and web portal share one JSON config but the desktop renderer has no status model to share. Whatever status/grouping concept is built must live in the shared model so all three surfaces agree, or the redesign just moves the flatness between surfaces.

=== CROSS-TOOL PATTERNS (recurring signals) ===
- Collapsible grouped rows with a counted, status-rolling-up header (signal/noise separation) - group the wall into named sections like 'My Dev Servers' / 'System & OS', collapse the noise by default, show a count badge per header  [seen in: Docker Desktop (Compose project parent rows), OrbStack (project grouping), Laravel Herd (grouped sites), VS Code Tree View (collapsible groups), Mullvad (country/city tree), Activity Monitor / Task Manager (Apps vs Background/System split), Git GUI clients (Local/Remotes/Tags groups), TablePlus (connection groups), k9s / Linear (status groups)]
    This is the single most-recurring pattern and the direct cure for PortPilot's headline complaint. Every researcher named it as the highest-leverage move. Auto-classifying ports into Dev / Other / System and collapsing System by default makes the 2-3 real dev servers sit alone at the top and the ~28 OS ports fold to one line.
- Leading colored status dot in a fixed left gutter, reinforced by a state word and (for accessibility) a shape difference - read pre-attentively down a single column  [seen in: Docker Desktop, OrbStack, Tailscale, DBngin, Vercel / Railway / Render (status pills), GitHub Actions (shape-coded glyphs), VS Code (ThemeColor status icons), Activity Monitor / Task Manager, Git GUI clients, TablePlus (status color)]
    PortPilot has zero status concept today. A green=running / grey=stopped / amber=conflict / red=error dot in column 1, paired with a word and a shape (filled disc vs hollow ring), is the cheapest high-impact win. It survives all 6 themes if driven by a per-theme CSS variable, and it makes 'find the problem' a one-saccade column scan.
- Master-detail (list + inspector) - keep list rows light and scannable, push verbose per-item depth (full command, PID, cwd, uptime, logs, kill confirm) into an on-demand side drawer or panel  [seen in: Docker Desktop (drill-in tabs), OrbStack (Info/Logs/Terminal/Files), Raycast (List+Detail split), Tailscale (windowed mode), Activity Monitor (process inspector), Git GUI clients (commit inspector), TablePlus / Postman (sidebar + detail), 1Password (item list + detail), Vercel / Render (list row to detail page)]
    Directly fixes the overloaded-yet-truncated card. The truncated COMMAND finally gets full width in the inspector, rows shrink to ~26-32px, and copy/kill move off every card into the detail surface. Adds a second altitude of information the flat grid has nowhere to put.
- Left-rail navigation instead of horizontal top-tabs - a vertical icon+label rail that frees vertical space, scales past 5 destinations, and mirrors the VS Code activity bar the user already knows  [seen in: Docker Desktop, OrbStack (source list), Laravel Herd / DBngin, Raycast (settings), Vercel / Railway / Render, Git GUI clients, Process monitors, Settings UIs (macOS / VS Code / 1Password)]
    Kills the vertical-space-wasting gold-underline tab strip and the ~5-tab ceiling. The active item gets the gold accent as a left-edge marker. Unifies the mental model with the existing VS Code extension surface.
- Reconcile registered apps with their live ports in ONE list - a registered app row shows its live port, status dot, and start/stop inline; unmatched live ports sit in a separate 'discovered/unregistered' group with an 'adopt as app' action  [seen in: OrbStack, Docker Desktop, DBngin, Render / Railway (declared vs actual in one row), Git GUI clients (branch + ahead/behind), Activity Monitor, VS Code Ports (Running Process column)]
    Ends the My Apps vs Active Ports tab split. 'Is my app running and where' becomes one row, one glance. The unregistered group is also the natural home for OS noise, deprioritized below the user's real apps.
- Hover-revealed contextual actions, show Start XOR Stop never both, demote destructive actions behind hover/overflow and a confirm - gate kill off system ports entirely  [seen in: Docker Desktop (hover inline cluster), OrbStack (hover actions), VS Code (group:inline hover icons + contextValue gating), DBngin (one dominant action), Vercel / Render (hover + overflow kebab), Raycast (cmd-K action menu), TablePlus (right-click verbs)]
    Removes the ~66 always-on buttons. A running row shows Stop, a stopped row shows Start, never both. System-classified ports hide or disable kill (a contextValue-style gate), fixing both the visual noise and the kill-a-Windows-process footgun.
- Persistent fuzzy search/filter plus quick-filter chips over a structured (grouped, sorted) list, with a remembered default view and per-group / segmented counts  [seen in: Raycast (fuzzy search), Docker Desktop (search + state filter), Activity Monitor / Task Manager, Tailscale / Mullvad (search-to-filter), Postman / Linear (filter chips + saved views), Git GUI clients (scoped filter), VS Code Settings (search + @modified)]
    Upgrades the lone filter box + '33 ports' badge into search + one-tap lenses (Mine / Dev / System / Conflicts) + a sort, persisted in the JSON config so the user lands on signal every launch. Filtering is the mechanism that lets one list hold both signal and noise.
- Settings as a category sub-nav + focused detail pane (not a flat box stack), with theme pickers as live-preview swatch tiles and typed inline controls (toggle / segmented control / stepper) plus one-line helper text  [seen in: Raycast (gold-standard prefs), VS Code Settings, macOS System Settings, 1Password, Laravel Herd (prefs sidebar), Arc (theme swatches), Linear / Postman]
    Fixes the flat settings stack. Theme becomes a swatch grid where each tile is painted in its own palette (trivial with existing CSS variables). Scan-interval becomes a segmented control (Off/5s/15s/30s). Scales to future settings without a longer scroll.

=== THREE DIRECTIONS ===

--- Direction 1: Three-Pane Master-Detail Shell  (effort: L) ---
A persistent three-column desktop: a slim left nav rail (Ports / Apps / Knowledge / Settings), a grouped collapsible list in the middle, and a right inspector pane that fills with the selected item's full detail. The Git-GUI / TablePlus / OrbStack shell. Maximum hierarchy: three altitudes always on screen (scope, list, detail).
PROS: Most hierarchy of the three: three real altitudes (scope rail / grouped list / inspector) always visible, the strongest possible answer to 'very flat'. | Inspector gives the truncated command, PID, cwd, uptime a permanent home with full width; list rows shrink to one dense line. | Left rail kills the top-tab vertical-space waste and scales past 5 destinations; mirrors the VS Code activity bar the user already knows. | Selecting a row never navigates away, so the list stays put while you inspect - no back-button maze. | Settings reuses the exact same shell (category sub-rail + detail pane), so one layout serves the whole app.
CONS: Three columns can feel cramped in a small Electron window and is genuinely tight in the narrow VS Code sidebar (where it should degrade to two panes or the existing tree). | Most build effort of the three in a vanilla-HTML/CSS/JS renderer: persistent split panes, resizable splitters, selection-driven inspector state, empty-state handling. | An always-on inspector spends horizontal width even for users who just want to glance-and-kill; the inspector must be collapsible. | Risk of importing pro-tool heaviness (14-button toolbars, modal wizards) that PortPilot's tiny verb set does not need.
BEST IF: Choose this if PortPilot is meant to be a daily-driver power tool and you want the deepest, most durable hierarchy that also scales to a 100-port machine and future features (logs, groups, per-app config).

--- Direction 2: Grouped Collapsible Dense List (single view + slide-over drawer)  (effort: M) ---
One main view, no permanent third column. The card grid becomes a single dense sortable table grouped into collapsible counted sections (My Dev Servers / Other / System & OS, System collapsed by default). Each row leads with a status dot. Clicking a row slides a detail drawer in from the right that you dismiss. Nav can stay top-tabs (cheapest) or move to a left rail. The lightest-touch route that still attacks flatness directly.
PROS: Cheapest path that still fully attacks flatness: grouping + status dot + counts are pure CSS/JS over the existing data, no split-pane plumbing. | The single highest-value fix (collapse System & OS to one line) lands immediately and is the bulk of the perceived win. | Table-over-cards roughly triples on-screen density and gives aligned columns you can scan vertically. | Drawer is optional and dismissible, so quick glance-and-kill flows stay one click; depth is opt-in. | Lowest risk on the no-framework renderer; can ship grouping first, drawer second, as two increments.
CONS: Less hierarchy than the three-pane shell: detail is hidden until you open the drawer, so the resting view is two altitudes not three. | If nav stays as top-tabs, the vertical-space and 5-tab-ceiling problems remain (can be fixed separately by moving to a rail). | My Apps reconciliation still needs doing; this direction leans on the group structure ('My Dev Servers' = matched apps) rather than a dedicated unified surface. | A slide-over drawer that covers part of the list can feel less stable than a permanent inspector.
BEST IF: Choose this if you want the maximum flatness reduction for the least build risk on a vanilla renderer, and you are happy to ship the win in increments (grouping first, then drawer, then optional rail).

--- Direction 3: Status Dashboard + Drill-In  (effort: M) ---
Lead with orientation. A pinned summary header ('3 dev servers running, 1 conflict, 33 ports') sits above a compact status board. The user's real dev servers render as a small pinned 'My Stack' band of richer rows (status dot, live port-as-link, uptime, one toggle); everything else collapses into quiet grouped sections below. Mullvad/Tailscale/PaaS feel: one glanceable health surface, detail one drill-in deep. Optimised for 'is my stuff up?' at a glance rather than dense list management.
PROS: Best 'is my stuff up?' glance: the summary header + pinned My Stack band answers the user's real daily question before any scrolling. | Strongest signal/noise separation by spatial promotion: the user's servers are physically lifted out of the list, OS ports sink into collapsed sections. | Conflicts get a dedicated, actionable callout instead of being lost in the grid - PortPilot's most actionable bad state finally has a home. | Naturally supports the tray/menu-bar quick-glance mode (Tailscale/Mullvad), and the summary feeds the VS Code 'PP: N running' counter directly. | Feels modern and calm; great first-impression surface.
CONS: The My Stack card band reintroduces cards, which are less dense than rows - fine for 3-5 pinned apps, poor if the user pins many. | Two visual languages (rich pinned cards on top, dense grouped rows below) is more design surface to get right and keep consistent across 6 themes. | Drill-in is a full-view swap (more like Docker's page navigation), so it needs a clean breadcrumb/back affordance to avoid a navigation maze. | Least suited to dense bulk list work; it optimises orientation over management. | Pinning is a manual concept the user must maintain (though it can default to matched registered apps).
BEST IF: Choose this if the primary job is reassurance and orientation ('are my servers up, any conflicts?') rather than dense management of many ports, and if a tray/glance mode is on the roadmap.

=== RECOMMENDATION ===
>> Grouped Collapsible Dense List (single view + slide-over drawer), evolving toward the Three-Pane Shell
The research is overwhelmingly consistent: across all 13 studies the single most-named fix is collapsible grouping with counted headers that separates the user's dev servers from OS/system noise, paired with a leading status dot. That is the spine of the redesign and it is exactly what the Grouped Collapsible Dense List delivers first and cheapest. The user's headline complaint is 'very flat' and their single most important win is separating real dev servers from OS noise - grouping plus status dot attacks both directly with pure CSS/JS over existing data, no split-pane or framework plumbing, which respects the vanilla-HTML/CSS/JS no-framework constraint. The three-pane shell (Direction 1) produces more hierarchy but is L-effort and risky on a no-framework renderer; the dashboard (Direction 3) optimises glance over management and reintroduces cards. The pragmatic path is to ship Direction 2's grouping, status model, and unified apps+ports list as P0, add the slide-over drawer as P1, and add the left rail and a settings sub-nav as P1/P2. The drawer and rail are the same primitives the three-pane shell needs, so this is not a dead end - it is the three-pane shell built incrementally, lowest-risk-first. Crucially the status model and grouping classification must live in the shared JSON config and a single statusOf(item)/classify(item) function so the desktop, VS Code tree, and web portal all read the same source of truth and stay in sync.
Per-surface changes:
  [all] Define the shared model first: a classify(port) function returning Dev / Other / System (Dev = matches a registered app or a known dev runtime like node/vite/next/python in the 3000-9000 range; System = svchost/System/PID 4/well-known OS ports 135/139/445; Other = the rest) and a statusOf(item) returning {state, color, glyph, label} for the 5-state model (running=solid green disc, stopped=hollow grey ring, starting=amber pulse, conflict=amber triangle, error=red circle-x). Store group-collapse state, pins, and last-used filter/sort in the shared JSON config so all three surfaces agree.
  [desktop] Replace the Active Ports two-column card grid with a single dense sortable table grouped into collapsible counted sections: MY DEV SERVERS (expanded) / OTHER USER PORTS / SYSTEM & OS PORTS (collapsed by default). Each header carries a disclosure chevron, a count badge, and a roll-up status dot. This is the P0 win.
  [desktop] Lead every row with a fixed-gutter status dot that differs by SHAPE not just hue (filled disc vs hollow ring) so it survives greyscale and all 6 themes; pair it with a short state word. Drive the dot color from a per-theme CSS variable. Make the :PORT a clickable link that opens http://localhost:PORT.
  [desktop] Merge MY APPS into the same surface: a registered app is a row in MY DEV SERVERS showing its live resolved port + uptime when running, or a Start affordance when stopped. Unmatched live ports fall into OTHER/SYSTEM with an 'Adopt as app' action. The standalone My Apps top-tab disappears as a primary destination.
  [desktop] Move per-row actions to hover-reveal, show Start XOR Stop (never both), and gate kill off System-classified rows (hidden or disabled with a 'Windows system process' warning + typed confirm). Add a slide-over right drawer on row click holding the full untruncated command, PID, cwd, uptime, and the copy/kill/open actions (P1), so rows stay ~26-32px.
  [desktop] Upgrade the lone filter box + '33 ports' badge into search + quick-filter chips (Mine / Dev / System / Conflicts) + a sort dropdown, persisted in config. Add a compact summary line ('3 dev running - 1 conflict - 33 total') in the top bar or status strip.
  [desktop] Rebuild Settings as a category sub-nav (Appearance / Scanning / Data / About) + focused detail pane (P1/P2). Render the 6 themes as live-preview swatch tiles each painted in its own palette with a ring on the selected tile. Make scan-interval a segmented control (Off/5s/15s/30s) and auto-scan a toggle with one-line helper text. Optionally move primary nav to a left icon rail with the gold accent as a left-edge marker (P2).
  [vscode] Apply the same model to the two tree views: lead each TreeItem with a ThemeIcon('circle-filled') colored by a ThemeColor status token, use label + dimmed description (e.g. 'node :3000' + 'PID 18244 - next dev'), group via TreeItemCollapsibleState with System collapsed, and gate the kill command behind a contextValue so it never appears on system ports. Feed the same running count to the existing 'PP: N running' status-bar item. In the narrow sidebar keep the tree (do not force a third pane).
  [web] The web portal renders the same renderer, so it inherits grouping, the status-dot model, the unified apps+ports list, and the drawer automatically once the desktop renderer is updated. Verify the per-theme status CSS variables and the collapse/pin/filter state read correctly from the shared config when served over the loopback agent.
